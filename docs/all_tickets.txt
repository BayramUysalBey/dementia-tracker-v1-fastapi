    • The Task

    • Current Behavior: The developer is unfamiliar with iterative software development. They may not know the purpose of daily meetings, how tasks are prioritized, or the roles within a Scrum team.
    • Expected Behavior: The developer understands the core values of Agile and the specific rituals of Scrum. They can confidently participate in Sprint Planning, Daily Stand-ups, and Retrospectives while understanding their specific responsibilities.
      Acceptance Requirements:
    • To consider this task "Done", the developer must complete the following:
    • Agile Mindset: Read and understand the 4 core values of the Agile Manifesto.
    • Scrum Roles: Identify the responsibilities of the Product Owner, the Scrum Master, and the Development Team.
    • Scrum Ceremonies: Explain the goal of the following four meetings:
    • Sprint Planning: Deciding what to do next.
    • Daily Stand-up: Quick daily sync on progress and blockers.
    • Sprint Review: Demoing the finished work.
    • Sprint Retrospective: Discussing how to improve as a team.
    • Artifacts: Understand what a Product Backlog and a Sprint Backlog are.
    • Definition of Done (DoD): Understand the concept of "Done" (ensuring a task is not just coded, but tested and ready).
    •  
    • Technical Implementation Details
    • The Agile Mindset (4 Core Values)
    •  
    • Agile is not a set of rules, but a way of thinking. The Agile Manifesto prioritizes:
    •  
    • Individuals and Interactions over processes and tools.
       
    • Working Software over comprehensive documentation.
       
    • Customer Collaboration over contract negotiation.
       
    • Responding to Change over following a plan.
       
    • Scrum Roles: Who does what?
    •  
    • Product Owner (PO): The "Voice of the Customer." They decide what needs to be built and maintain the Product Backlog.
       
    • Scrum Master: The "Coach." They ensure the team follows Scrum values and remove blockers (like a broken environment or missing MRI results).
       
    • Development Team: The "Builders (Creators)" (Me, the Seniors, and the Beginners). They decide how to build the tasks assigned.
       
    • Scrum Ceremonies: The Rituals
    •  
    • Sprint Planning: At the start of a Sprint (usually 2 weeks), the team picks tasks from the Backlog to finish.
       
    • Daily Stand-up: A 15-minute sync. We answer three questions:
       
    • What did I do yesterday?
    •  
    • What will I do today?
    •  
    • Do I have any blockers?
    •  
    • Sprint Review: A "Show and Tell." We demo the working code to the stakeholders.
       
    • Sprint Retrospective: "Team Therapy." We discuss what went well and what we can improve in the next Sprint.
       
    • Artifacts: The Lists
    •  
    • Product Backlog: The "Master List" of everything the project might ever need.
       
    • Sprint Backlog: The "To-Do List" for the current 2-week cycle.
       
    • The Definition of Done (DoD)
    •  
    • The DoD is a comprehensive checklist of necessary criteria that ensures the increment is at the desired quality and is truly "done".
    • This includes all the work that must be done for the working increment to be useful and releasable and could consist of things like writing code, testing, documentation, and meeting regulatory requirements.
    • It is crucial for transparency and ensuring the Increment is respecting the standards of the organisation or the product and also satisfies the Scrum Team's quality standards.

CAT-28 Common Tech Industry Jargon

    • The Task
    • The objective of this task is to familiarize the developer with the essential technical language and slang used in modern software development. By understanding these terms, the developer will be able to communicate effectively during technical discussions, understand documentation, and participate in code reviews.
    • Behavior: Current vs. Expected
    • Current Behavior: The developer may feel confused or lose track during technical meetings when terms like "Technical Debt," "CI/CD," or "Refactoring" are used. They might not fully understand the specific language used in pull requests or system architecture discussions.
    • Expected Behavior: The developer can follow technical conversations comfortably. They should be able to use the correct terminology to describe their work, ask technical questions clearly, and understand the context of development workflows.
      Acceptance Requirements:
    • To consider this task "Done", the developer should be able to explain and understand the following categories of jargon:
    • Development & Code:
    • Refactoring: Improving code without changing its behavior.
    • Technical Debt: The "cost" of choosing an easy solution now instead of a better one that takes longer.
    • CRUD: Create, Read, Update, Delete.
    • Git & Collaboration:
    • Pull Request (PR) / Merge Request: Proposing changes to the code.
    • Code Review: The process of teammates checking each other's code.
    • Conflict: When two people change the same part of the code at once.
    • Deployment & Environments:
    • Local vs. Staging vs. Production: Where the code is running (your machine vs. testing vs. live for users).
    • CI/CD: Automated ways to test and deliver code (Continuous Integration/Deployment).
    • System Architecture:
    • API: How different software talk to each other.
    • Frontend vs. Backend: The part the user sees vs. the logic and database.
    • Legacy Code: Old code that is still being used but might be hard to maintain.
    •  
    • Technical Implementation Details
    • Development & Code:
    •  
    • Refactoring: Cleaning up the internal structure of the code without changing what it does.
       
    • For example: Moving to Flask routes into Blueprints. The app still works the same, but the code is much cleaner.
    •  
    • Technical Debt: Choosing a "quick and sloppy" solution now will require more work to fix later.
       
    • For example: Writing the database URL directly into your code instead of using a .env file. Time might be saved now, but personal data could be inadvertently exposed later if not corrected for deployment.
    •  
    • CRUD: The four basic functions of persistent storage: Create, Read, Update, Delete.
       
    • For example: In my Dementia Tracker app, creating a new symptom log is "Create"; viewing the list is "Read."
    •  
    • Git & Collaboration:
    •  
    • Pull Request (PR) / Merge Request: A formal request to merge your code changes into the main project. It’s where the team reviews the work.
       
    • Code Review: This is the process where a senior developer reviews a submitted piece of code to check for errors, styling mistakes, or logical inaccuracies before the code is released.
       
    • Conflict: This occurs when two developers modify the same line of code in different ways. Git doesn't know which change to keep, so it needs to be "resolved" manually. Alternatively, it could be a conflict between different programs or systems.
       
    • For example: Centralizing the database initialization logic into a single instance/orchestrator to prevent conflicts (Docker issue in the Dementia Tracker app).
    •  
    • Deployment & Environments:
    •  
    • * Local vs. Staging vs. Production:
    •  
    • ** Local: Code running on your own computer (laptop, desktop, etc.).
    •  
    • ** Staging: A "copy" of the live environment where we test the code before real users see it.
    •  
    • ** Production: The "live" environment. Real users and real data reside here.
    •  
    • CI/CD (Continuous Integration / Continuous Deployment): Automated pipelines that run your tests (like Pytest) and deploy your code to the server every time you push to GitHub.
       
    • System Architecture
    •  
    • API (Application Programming Interface): A set of rules that allows your backend application to communicate with the frontend or another service (such as a weather or live currency API).
       
    • Front-end and Back-end:
      ** Front-end: The "face." HTML/CSS/JavaScript. The part the user sees and clicks on.
    •  
    • ** Back-end: Where the logic and data reside.
    •  
    • Legacy Code: Code inherited from the past. It may be written in an old, cluttered, or outdated style, but the business depends on it.

CAT-29 Understanding the Software Development Life Cycle (SDLC)

The Task
The objective of this task is to help the developer understand the standard end-to-end process of creating a software product. Instead of seeing coding as an isolated activity, the developer will learn the phases a project goes through from the initial idea and planning to testing, delivery, and long-term maintenance.
 
Behavior: Current vs. Expected
    • Current Behavior: The developer may think that software development is only about writing code. They might not understand why certain steps like requirement gathering or quality assurance happen before or after the coding phase.
    • Expected Behavior: The developer understands that coding is just one part of a larger cycle. They recognize the importance of each phase like Planning, Design, Testing, etc. and understand their role within that entire lifecycle.
 
Acceptance Requirements:
To consider this task "Done", the developer must be able to describe the following 6 stages of the SDLC:
Requirement Analysis: Gathering information about what the user needs and what the software should do.
Design: Planning the architecture, user interface, and technical structure of the software.
Implementation (Coding): The actual process of writing the code based on the design.
Testing (QA): Finding and fixing bugs to ensure the software works as expected and meets the requirements.
Deployment: Releasing the software so that users can actually start using it.
Maintenance: Monitoring the software, fixing new issues, and making updates over time.
 
Technical Implementation Details
Software Development Life Cycle (SDLC):
 
    • Requirement Analysis:
 
Before writing code, we need to understand the problem.
Gathering specific details about what the software needs to do and who it's for.
For example: The requirement for a Dementia Tracker App was: "As a caregiver, I need to record daily symptoms and their severity so I can share them with doctors."
 
    • Design:
 
Before producing the product, we must plan.
Designing the database schema (myssql, postgresql, nosql, etc.), choosing the technology stack, and planning the code structure (like Blueprints).
For example: Deciding to use PostgreSQL for data persistence and Docker to ensure the application runs the same way on any machine.
 
    • Implementation:
 
The process of writing the code.
Translating the design into machine-readable instructions.
For example: Building routes and logic using Flask (its framework) based on Miguel Grinberg's tutorial.
 
    • Testing:
 
Ensuring the code works and doesn't break anything else.
Finding bugs and verifying that requirements are met.
For example: Using Pytest to verify that the symptom log is correctly saved to the database for the Dementia Tracker App, or manually checking that Docker containers are connected correctly.
 
    • Deployment:
 
Moving the code (project) from the computer to a server accessible to users.
The "go-live" process.
For example: Render | The cloud for builders or Host, run, and code Python in the cloud: PythonAnywhere 
 
    • Maintenance:
 
Fixing new bugs, updating security patches, and adding new features based on user feedback.

CAT-30 Professional Collaboration & Communication

The Task
The objective of this task is to teach the developer how to work effectively within a professional software team. Software development is a team sport, so this task focuses on how to share ideas, give and receive feedback, and communicate progress clearly to ensure the team moves forward together.
Behavior: Current vs. Expected
    • Current Behavior: The developer may work in isolation, provide vague updates like "I'm still working on it", or take code review feedback personally. They might not know when to ask for help or how to document their decisions for others.
    • Expected Behavior: The developer communicates proactively. They provide clear updates on Slack/Jira, participate constructively in code reviews, and follow the "30-minute rule" (asking for help after being stuck for 30 minutes). They understand that feedback is about the code, not the person.
 
Acceptance Requirements:
To consider this task "Done", the developer must demonstrate an understanding of the following communication standards:
Effective Status Updates: Learn how to give a concise update during Stand-ups (What I did, What I will do, and any Blockers).
Asynchronous Communication: Use Slack and Jira effectively by providing enough context in messages so that others can understand the issue without needing a meeting.
Code Review Etiquette:
Giving Feedback: Learn to suggest improvements politely like "What do you think about..." instead of "This is wrong".
Receiving Feedback: Understand how to treat code suggestions as a learning opportunity rather than a personal critique.
The "Ask for Help" Rule: Understand the balance between trying to solve a problem independently and asking for help before wasting too much time.
Documentation: Learn the importance of writing clear comments in code and updating project notes so that teammates can follow your work.
 
Technical Implementation Details
Professional Collaboration & Communication
 
    • Effective Status Updates (The"Stand-up" Format)
 
Three-point update to inform the team:
What I did: For example, "I reworked the Dementia Tracker App project in the Blueprint to make it more understandable."
What I will do: Edit the HTML files in the Blueprint as well.
Obstacles: I'm struggling with an ElasticSearch compatibility issue.
 
    • Asynchronous Communication (Slack & Jira)
 
 
Since we are a remote team, I will try to provide complete and clear information in messages.
Example:
Problem: "It's not working!"
Context: "I'm getting a 500 error on the /login route. I checked the logs and it shows a database connection timeout."
Goal: The team's time is not wasted and a goal-oriented solution is found.
 
    • Code Review Etiquette
 
Example:
Giving Feedback: "I" statements or questions can be used. Instead of saying "This is wrong," use phrases like, "How would you evaluate using a Blueprint here to ensure consistency with the rest of the application?"
Getting Feedback: Code is a product; it doesn't reflect personality or character. A response like, "I get it, thanks for the hint! I'll update it now," is acceptable.
 
    • The "30-Minute Rule" (Asking for Help)
 
To balance independence and team speed:
Spend 30 minutes solving the problem. (Documentation, YouTube, AI, or Newest Questions ). If the problem cannot be solved, ask for help.
 
    • Documentation & Comments
 
Code Comments: Include not only "What" but also "Why." Be descriptive for the team and the person who will edit the code on the next return.

Real-time GPS and Geo-Restriction integration ensures the core value of "Continuous

Data."

Through "How are you?" features and "Relaxation Mode" and Meditation tracking, the
application treats the caregiver as a critical component of the medical system.
Impact: A healthy caregiver is the patient's best resource. By monitoring the caregiver's
stress levels and encouraging regular exercise and leisure time, the application acts as an
"Early Warning System" for burnout. This ensures that care remains sustainable in the long
term and prevents the collapse of the home care environment.
4. Operational Efficiency (Backend Value)
Thanks to the automatic data cleanup feature after reporting, the system provides a
high-performance and low-cost infrastructure.
Impact: For the user, this means a fast and responsive application that doesn't slow down
over time. For the provider, this means a lean database architecture that prioritizes current
and relevant data and archives historical data in portable PDF formats.

Interview Preparing Phase:
Research the following questions and add them (with answers) to your notes.
Theoretical:
What is the main advantage of using "APIRouter" in a large-scale FastAPI project?
The main advantage is modularity and separation of responsibilities. In a large project, putting all routes into a single "main.py" file becomes unmanageable as the project progresses. "APIRouter" allows the API to be broken down into smaller, logical mini-applications (e.g., "users.py," "orders.py").
This makes the codebase:
Easier to navigate: Developers know exactly where to find specific logic.
Cleaner: Instead of repeating dependencies, prefixes, and labels for each endpoint, we define them once at the router level.
What is the Service Layer pattern and how does it improve code testability?
The Service Layer acts as an intermediary between API endpoints (transport layer) and database models (data layer). The business logic resides here.
Without the service layer, your logic would be stuck inside the route functions. To test this, you need to simulate HTTP requests. With the service layer, you can write unit tests for your business logic functions independently of FastAPI or your database, making the tests faster and more reliable.
Why use BaseSettings from Pydantic instead of os.getenv()?
While "os.getenv()" works for small scripts, "BaseSettings" is superior for professional backend development.
Type Validation: Prevents runtime errors by ensuring PORT is an integer and DEBUG is a boolean.
Centralization: All configuration is defined in a single class instead of being scattered across the application.
Fast Error Detection: If a required environment variable is missing, the application will crash immediately with a clear error message at the outset, rather than failing later when a specific function is called.
What is the role of the app/core/settings.py file in a professional project?
In a professional environment, app/core/settings.py acts as the "Single Source of Truth" for application configuration. This includes:
Loading variables from .env files.
Defining global constants (e.g., API keys, Database URLs, JWT secrets).
Customizing settings based on environment (Development, Test, Production).
Providing a single "settings" object that other modules in the application can import.
How does "include_router()" work; what are the "prefix" and "tags" parameters?
include_router() is the method used in the "main.py" file to register the routers you create.
prefix: This adds a string to all routes in that router. For example, the prefix "/users" means that a route defined as @router.get("/") becomes accessible from "/users/".
tags: This is primarily for documentation purposes. This makes it much easier for front-end developers to read your API documentation by grouping routes in Swagger UI (OpenAPI).
What is "SettingsConfigDict" and how does it bind a Python class to a .env file?
"SettingsConfigDict" is a configuration class used inside the Pydantic "BaseSettings" model.
It binds the class to a .env file using the env_file attribute. For example:

class Settings(BaseSettings):
db_url: str
model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8")

When the "Settings()" class is created, Pydantic automatically searches for a file named .env, reads the values, and maps them to the class properties.
